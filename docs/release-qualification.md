# Release qualification observations

[Issue 6](https://github.com/patchwerks/patchwerks/issues/6), PW-0.4, adds a read-only observer and proposal generator. It cannot publish, approve, merge, deploy, create tags or write the integration lock. Required independent review and owning-product acceptance remain separate gates. Use trusted, reviewed Python/Git/gh executables and this script from the accepted coordinator revision. Run against a trusted clone with trusted configuration and a stable filesystem, never an attacker-controlled Git configuration, executable search path or credential environment. A trusted publisher may supply its narrowly scoped read credential to gh; candidate tests must receive no credential at all.

`python3 scripts/release_preflight.py publication --base-repository example/coordinator --head-repository contributor/coordinator --base-ref main --head-ref issue-6 --expected-head FULL_HEAD_SHA --expected-base FULL_BASE_SHA --base-repository-id 10 --head-repository-id 20 --number 123` reads the fixed github.com REST PR route and exact head branch with `git ls-remote`, then repeats both observations. Numeric repository IDs, repository names, returned PR number, refs and exact supplied base/head commits must agree. Numeric IDs reject booleans. Success is `publication_observed: true`, `execution_authorized: false`. This is a bounded observation, not a lease: a push after the final observation still requires fresh acceptance. No checkout is consulted, so dirty local files do not alter the published commit claim. Git credential helpers are disabled for this public remote read. Git subprocesses discard ambient GIT_* variables, disable global/system configuration, lazy fetch and terminal prompting, and retain the trusted executable search path. Private publication transport is outside this bounded observer.

`python3 scripts/release_preflight.py release --repo /trusted/clone --tag v1.0.0 --accepted-commit FULL_SHA --expected-tag-object FULL_TAG_OBJECT_SHA --archive /trusted/artifact.tar --digest FULL_SHA256 --size 123` requires an annotated tag directly targeting the accepted commit. Both tag object identity and commit identity are pinned; a new annotation at the same commit is a retag and fails. Git replacement objects are disabled. VERSION must be a blob and is read from the commit, preserving the owning repository's authority. The archive must be a bounded regular file with no symlink path components; bytes are hashed without extraction and compared to the expected size and SHA256. This does not establish correspondence between those bytes and a reproducible build or provider release asset. Supply those facts through separately accepted build/provider provenance. The local working tree is intentionally irrelevant to commit inspection; creating an actual release still obeys the clean-worktree rule in [release policy](releases.md).

`python3 scripts/release_preflight.py lock --current workspace.lock.json --proposal /trusted/proposal.json` reads the current lock and prints proposed lock bytes only to stdout. The proposal has exactly one `changes` array; each change contains `id`, `old_revision`, `revision`, `tests`, `migration`, and `rollback`. Old and new revisions must be full commit SHAs; IDs must already be enrolled, occur once, and match the current revision. Only revision fields change. VERSION authority, agentile pin, visibility, repository identity and all other metadata are retained. The three evidence values are nonempty provenance references supplied by the caller, **not verified acceptance**. Review the references, contract compatibility and consumer acceptance independently before proposing any actual integration PR. A rollback uses the same format with the now-current old revision and previously accepted target revision. Duplicate/unknown JSON keys, nonfinite values, boolean schema/size values and unknown product IDs fail closed. JSON inputs must be bounded regular files without symlink path components; nonblocking opens reject FIFOs. CLI failures use static diagnostics rather than echoing input.

## Qualification and limits

The supervisor should run `python3 -m unittest discover -s tests -p 'test_release_preflight.py'` in a disposable credential-free sandbox. Synthetic transport tests independently exercise fixed GitHub routes, repository IDs, returned PR number, stale base/head and changed readbacks. They do not represent live GitHub observations. The remaining fixtures use real temporary Git repositories, annotated/lightweight tags, retags, replacement refs, archive bytes, and synthetic lock IDs. They do not run candidate code on a privileged publisher.

Run `PATCHWERKS_JJ=/absolute/path/to/jj python3 -m unittest discover -s tests -p 'test_jj_publication.py'` in that same sandbox for explicit real-jj qualification. Without the variable the test reports an unavailable skip; supplying a missing executable fails. The fixture uses an isolated HOME/config and local bare remote, creates and describes a change, publishes an explicit bookmark, reads back its full commit, and requires a stale push to fail after a second writer changes the remote. It then exercises a separate Git-managed synthetic submodule checkout and exact gitlink. It does not rely on hooks. Installed official jj 0.46.0 help was inspected; `--allow-new` is not used.

A passing local fixture qualifies only those local operations. The actual coordinator fork PR, remote head, checks and independent approval must be observed separately by the supervisor and recorded with exact IDs; no hosted publication is claimed by these tests. The synthetic submodule fixture does not qualify jabberwerk, its private source, its full dependency tree, LFS, or product acceptance. See the existing [jj contract](jj.md) and its [official compatibility reference](https://docs.jj-vcs.dev/latest/git-compatibility/). No CI download workflow or private content is introduced.
